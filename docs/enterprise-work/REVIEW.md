## Original findings — all resolved on focused rereview

### R1 — P1: recovery silently removes the SSO-required policy

Evidence: `scripts/product-maintenance.mjs:25` and `:39` allowlist only pre-Enterprise configuration and volumes. Backup copies those lists at `:237` and `:254`; restore copies only the same files at `:416` and reloads product configuration at `:432`. `scripts/enterprise-manifest.mjs:8` treats the resulting missing Enterprise manifest as disabled. `server/product.ts:105–128` consequently constructs the application without Enterprise identity; `server/app.ts:90` omits `ssoRequired`. Recovery only bumps account revisions (`infra/product/recovery.ts:32`); it preserves existing local password verifiers and active administrator roles.

An ordinary bootstrap administrator can remain unlinked when SSO is enabled without any configured break-glass account. Its password is correctly denied in Enterprise mode, but is accepted after the described restore into local mode. This also reenables local recovery and authority management. Paused agents do not prevent the newly authenticated administrator from changing control state. This is a policy downgrade, not merely a missing convenience setting.

Targeted verification: a synthetic in-memory SQLite account was initialized, denied password login under `{ssoRequired:true}`, subjected to the same recovery invitation/recovery invalidation and revision bump, then authenticated through the restored local-mode `ManagedAccounts` constructor. Observed output: `ssoPasswordDenied:true`, `restoredLocalRole:"administrator"`, `restoredAssurance:null`. No actual restore or Docker resources were used; filesystem/startup implications above are established by the caller code.

Fix: preserve an authenticated nonsecret Enterprise-required marker in backup/installation state and refuse ordinary startup until the restored installation has explicitly provisioned and validated its new Enterprise authority/configuration. Do not silently copy endpoints/secrets as a substitute for that decision. A bounded interim refusal to back up/restore Enterprise installations is safer than accepting a downgrade. Test that ordinary pre-SSO accounts cannot regain access through restore, and that missing Enterprise configuration cannot be treated as compatibility mode when the marker is present. Document cursor/installation-ID recovery and replay semantics explicitly.

### R2 — P1: the mandatory HTTPS ingress removes the SCIM service credential

Evidence: `infra/product/https-ingress.mjs:31` unconditionally excludes `authorization` before forwarding to the dashboard. Enterprise configuration requires a dedicated HTTPS installation (`scripts/enterprise-config.ts:8`). The inner proxy expects that bearer for machine mutations (`apps/dashboard/lib/control-proxy.ts:51–52`) and forwards it for SCIM (`:85`); SCIM requires it (`server/security/enterprise-scim.ts:62`). Therefore real HTTPS SCIM mutations fail at the proxy with 403, while collection reads reach SCIM without authentication and fail with 401. Provisioning and, critically, deprovisioning cannot operate on the deployed path.

Existing `tests/enterprise/proxy.test.ts` supplies the credential directly to the inner proxy and therefore misses the outer boundary. `tests/production/https.test.mjs` explicitly expects credential stripping on ordinary routes. Static caller-path evidence is conclusive; the parent is adding the actual TLS regression.

Fix: forward Authorization only for the explicitly supported canonical SCIM paths, retaining stripping on other routes and all existing host/origin checks. Exercise a real TLS ingress -> dashboard proxy -> SCIM request with the dedicated synthetic credential, plus wrong/missing bearer and non-SCIM credential stripping.

### R3 — P2: the proxy rejects bodyless SCIM DELETE

Evidence: `apps/dashboard/lib/control-proxy.ts:66–80` requires a JSON content type and parses JSON for every non-GET request. SCIM DELETE handlers (`server/security/enterprise-scim.ts:113`, `:149`) use only path, credential and optional ETag and do not require a body. Standard bodyless service DELETE therefore cannot reach the tombstone/offboarding transaction.

Targeted verification: invoked the real `controlProxy` with `DELETE /api/scim/v2/Users/u1`, correct public Host and a 32-character synthetic bearer, with no body/content type. Result: **415**, `JSON body required`, backend transport not invoked. This is independently reproducible after R2 is fixed.

Fix: permit an empty body specifically for supported SCIM DELETE routes while retaining bounded request consumption and rejecting unexpected payloads. Check real bodyless User/Group deletion, ETag failure, repeated deletion, and session invalidation through the complete request path.

### R4 — P2: accepted SCIM tokens exceed the proxy's credential grammar

Evidence: `server/security/enterprise-identity.ts:16` accepts SCIM tokens of 32–512 characters. `apps/dashboard/lib/control-proxy.ts:51` recognizes machine credentials only up to 256 characters. Thus valid configured tokens in the 257–512 range cannot perform mutations without a browser Origin header.

Targeted verification: `validateEnterpriseServices` accepted an otherwise valid synthetic configuration with a 300-character ASCII SCIM token. A no-Origin `POST /api/scim/v2/Users` passed that configured token to the actual proxy and returned **403**, backend transport not invoked.

Fix: align configuration and proxy on one header-safe, printable non-whitespace token contract and preserve the dedicated bearer check in SCIM. Test the accepted maximum, whitespace/invalid header input and over-limit rejection.
