## CI-enabled repository admission — proposed, not accepted

The first evaluated write profile remains a dedicated synthetic repository with Actions disabled and no active downstream automation. Contents/PR authority can trigger code execution even when Workflows editing is forbidden: an approved change to ordinary source, build hooks or package scripts can be consumed by an existing workflow. App token scope does not express file-path limits; the mediator's typed path/diff controls remain necessary. Do not market this as accepted protection for arbitrary repositories with CI.

Before admitting a specific CI-enabled staging repository, its owner must inventory push/pull_request/pull_request_target/workflow_run/reusable workflows, required checks, apps, organization hooks, bots, runner groups, environments and cloud-federation trust. The candidate profile must use unprivileged ephemeral jobs, no protected secrets or deployment authority, read-only workflow tokens, explicit network destinations and separate trusted review before any privileged follow-up. These are proposed prerequisites, not verified GitHub settings or a guarantee that all organization automation is discoverable by the App.

Acceptance cases in that separately authorized sandbox: allowed exact diff causes only listed check runs; adversarial source/package hook cannot read a sentinel credential or protected network target; fork/same-repo PR trust difference and pull_request_target paths are tested; cancellation/lost response/replay does not create duplicate branch/PR/job effects; branch/head changes invalidate the review; workflow edits/merge/deploy/release remain denied; an independent repository/runner owner reconciles actual jobs and external side effects. Failed or unobservable automation blocks profile admission. Do not enable Actions, alter workflow permissions or repeat the consumed finite live trial under this document alone.
