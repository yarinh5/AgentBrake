# Enterprise controls — operation and acceptance

Status: opt-in implementation under local validation. This guide does not authorize a customer connection, deployment or paid service. Preserve product-local; use a separate installation per organization. The Enterprise gap table distinguishes locally tested software from actual customer/operating acceptance.

## Enable on a dedicated installation

1. Prepare a dedicated HTTPS candidate using PRODUCTION_OPERATIONS.md. Bootstrap its managed owner account locally and verify an independent approver workflow. Do not use production identities/data for initial validation.
2. Stop that dedicated installation. Prepare an operator-owned bounded JSON configuration file; never send client secrets or service bearer tokens in chat. The configuration acknowledges `managedAccountsInitialized: true` and contains optional `identity` and/or `audit`. Identity fields and SCIM mappings are specified in enterprise-work/identity.md; audit fields are `endpoint`, `bearerToken`, optional `batchSize` (1–100), `timeoutMs` (100–10000) and `intervalMs` (1000–3600000). Require HTTPS. Audit sink acknowledgement is the exact protocol in enterprise-work/siem.md; a vendor adapter may be needed.
3. Run `node --import tsx scripts/configure-enterprise.ts <dedicated-name> <absolute-config-file>`. It rejects product-local, running services, existing Enterprise authority, testing bypasses, a callback origin that differs from the installation, and caller-selected state paths. A durable nonsecret Enterprise-required marker precedes credential/configuration commit. Secret config files stay in the private installation directory; operator Windows ACL/POSIX ownership review is required. No service is started by configuration.
4. After explicit authorization for the named IdP/sink, start the dedicated installation with `node scripts/product.mjs start <dedicated-name>`. Readiness refuses an uninitialized account store or invalid emergency administrator. The control process alone mounts Enterprise credentials. An isolated fixed-endpoint egress component forwards only configured token/JWKS/sink routes. Agent networks and credentials are unchanged. No token or browser input selects an outbound destination.
5. Provision users and mapped groups through `/api/scim/v2/Users` and `/api/scim/v2/Groups` using the dedicated bearer credential over the HTTPS entrypoint. Provision the explicit issuer/subject binding described in identity.md; email matching never grants access. Keep human administrator and approver identities distinct. Verify role changes/deactivation revoke existing sessions and pending sign-in.
6. Sign in using the organization button. Password/invitation/recovery fallback is disabled in SSO mode except the explicitly designated existing emergency administrator's password sign-in. That event is audited and does not claim MFA. Choose actual phishing-resistant IdP policy and matching signed assurance values with customer IT; strings alone do not establish physical authenticator assurance. Native SAML is not implemented; a SAML-to-OIDC IdP broker requires separate actual verification.

The operator-only `/api/enterprise/status` reports configured identity and audit-delivery state. A green process health endpoint is not proof that a sink has received events. Delivery is at least once; sinks deduplicate stable installation/sequence IDs. Failed/partial ACK, bad chain or failed checkpoint never advances the cursor. Stale crash lock recovery is an operator action after confirming there is no writer; preserve checkpoint and source audit. No infinite transient in-memory queue is used.

## Backup, recovery, keys and operations

Existing bounded encrypted cold backup remains the recovery source. `enterprise-operations.mjs` provides authenticated copying/verification, explicit retention preview, fresh availability/disk/certificate/backup checks and inert Linux timer templates. See enterprise-work/operations.md for exact CLI/config contracts. No timer is installed, file deleted or off-host destination inferred. A second directory on one computer is not an off-host backup. Health command exit2 includes missing evidence; it must be routed to an actual operator and exercised before operational acceptance.

The separate Enterprise evidence packet includes `enterprise-work/restore-acceptance.md` and the executed standalone harness. Actual local PostgreSQL backup/stopped recovery was exercised without mocking maintenance or Docker. It verifies preserved security requirements and data/audit/authority invariants; it does not claim an operationally resumed restored IdP/sink or off-host recovery. The fixture's elapsed time is not an RPO/RTO commitment.

Enterprise backup preserves required security mode; it does not export IdP/client/SCIM/SIEM credentials or silently reactivate them after recovery. Restored Enterprise installations remain stopped pending separately reprovisioned HTTPS and Enterprise configuration. Existing recovery invalidates sessions/invitations/recovery links and pauses task authority. Do not remove requirement markers to bypass this gate. Event cursor is not a recovery authority: a newly restored installation has a new identity and replays retained events under that installation ID; the sink must retain original records and distinguish recovery lineage. Reconcile target outcomes before resuming tasks.

Key rotation is staged: preserve encrypted backup/recovery custody separately, stop the candidate, provision new narrowly scoped external credentials through the operator's approved secret store, validate a fresh candidate, revoke old credentials only after the new route is verified, and preserve a rollback/incident record. Current software uses restricted files, not a native KMS integration. Do not claim provider-side revocation, key recovery or Windows ACL compliance from a local file-mode setting.

After a host/daemon interruption, first inspect the existing named containers and volume bindings and compare image IDs with the installation record. If the source checkout has changed, rebuilding is an upgrade decision, not a harmless restart. Resume only the known existing containers in dependency order when appropriate, then verify health and reconcile any uncertain target effects. Do not reset volumes or remove authority requirements to recover availability. The local interruption report in the separate evidence packet records one actual resumption on unchanged images; its cause remained unknown, and no pre-interruption transaction snapshot established byte-for-byte continuity.

`enterprise-signing.mjs` signs archive attestations with an operator-controlled Ed25519 key and verifies against independently supplied trust key, expected version and source hash. A checksum or locally generated signing key does not prove company identity or hosted build provenance. Keep private keys out of archives. Sign only after exact-source release/package verification; choose organizational key custody and distribution before external release.

## Data map and support boundary

| Data | Location/use | Retention and collection boundary |
|---|---|---|
| Password verifiers, OIDC issuer/subject, SCIM users/groups and revisions | Control identity store; authentication/provisioning | Account tombstones retained for replay/offboarding correctness; no password/token in UI exports |
| Pending OIDC verifier/state/nonce | Bounded process memory, 5 minute TTL | One use, lost on restart; never logged or included in evidence |
| IdP/client/SCIM/sink credentials | Dedicated control secret file | Operator controlled; never agent mounts or source/evidence archives |
| Tool arguments/review/audit, outcome/disclosure metadata | Control database | Existing result retention defaults24h; audit/review/arguments persist; no unsupported deletion promise |
| SIEM projection | Configured sink and local delivery cursor | Only allowlisted event category, sequence/time, stable ID and chain hashes; no raw arguments/results/email/error text |
| Support/evidence package | Explicit operator-selected release reports | Synthetic test data and hashes; inspect before sharing; no automatic upload |

Support procedure: collect source/image IDs, sanitized health statuses, exact failing action/correlation IDs and aggregate counts; exclude credentials, prompts, source code/customer records and raw database dumps. Preserve original audit privately. Obtain a named recipient and authorized retention before sharing. No external support telemetry is enabled automatically.

## Local versus external acceptance

Local regression, real synthetic IdP exchange, HTTP/TLS routing, fault injection, artifact tampering and backup exercises establish bounded behavior. Full report IDs/source hashes belong in SECURITY_EVIDENCE.md and the Enterprise evidence report after final verification. Customer IdP/SIEM interoperability, physical MFA, KMS, separate-host backup/restore, Linux VM, on-call routing, hosted CI/branch enforcement, independent human AppSec, legal/privacy terms and actual pilot outcomes remain external acceptance work. Single-instance restoration is not HA/PITR; measured local load is not an SLA. See ENTERPRISE_GAP_ANALYSIS.md for precise statuses.

MFA session freshness: an existing OIDC session can read within its8hour lifetime, but human control mutations require signed auth_time within configured maxAuthAgeSeconds again. A stale session receives401 before state change and must complete organization sign-in again. Logout remains available. This is an application freshness gate, not proof of the IdP physical authenticator.
